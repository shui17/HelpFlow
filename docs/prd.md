## 3 项目概述

HelpFlow 是一个通用企业客服工单管理系统。普通用户通过系统提交账号、产品、支付或技术问题；客服人员领取并处理工单；管理员负责工单分配、人员角色和账号状态管理。

系统以工单为业务核心，保存问题内容、当前负责人、用户与客服的回复、状态变化以及关键操作记录，使问题处理过程可查询、可追踪、可管理。

## 4 项目目标

### 4.1 用户目标

- 用户能够使用统一入口提交问题。
- 用户能够查看自己问题的处理进度。
- 用户能够与负责客服持续沟通。
- 用户能够确认问题是否真正解决。

### 4.2 客服目标

- 客服能够清楚查看待领取工单。
- 客服能够管理自己负责的工单。
- 客服能够按照统一状态流程处理问题。
- 客服不会与其他客服重复领取同一工单。

### 4.3 管理目标

- 管理员能够查看全局工单情况。
- 管理员能够分配和重新分配工单。
- 管理员能够调整普通用户与客服角色。
- 管理员能够启用和禁用账号。
- 管理操作能够被记录和追踪。

### 4.4 项目成果目标

- 完成能够本地运行的 Vue 3 前端。
- 完成能够本地运行的 FastAPI 后端。
- 使用 MySQL 持久化保存业务数据。
- 使用 Apifox 管理并验证主要接口。
- 三种角色可以通过浏览器完成各自的业务操作。
- 可以演示一张工单从创建到关闭的完整流程。

## 6 用户角色

### 6.1 普通用户 `user`

负责提交问题并确认处理结果，主要使用用户概览、我的工单、创建工单、工单详情和个人中心。

### 6.2 客服人员 `agent`

负责领取和处理工单，主要使用客服工作台、待领取工单、我负责的工单、工单详情和个人中心。

### 6.3 管理员 `admin`

负责系统管理，主要使用管理概览、全部工单、工单分配、用户管理和个人中心。

管理员默认不参与工单对话，也不能绕过正常状态流程直接改变工单结果。

## 7 核心业务流程

### 7.1 普通用户注册与登录

```text
进入注册页
    ↓
填写用户名、邮箱、密码和确认密码
    ↓
前端完成基础校验
    ↓
后端再次校验并创建普通用户
    ↓
跳转登录页
    ↓
登录成功并保存 Access Token
    ↓
获取当前用户信息
    ↓
进入普通用户首页
```

### 7.2 工单完整处理流程

```text
普通用户创建工单
    ↓
工单状态为 open，负责人为空
    ↓
客服主动领取，或管理员指定客服
    ↓
客服将工单改为 in_progress
    ↓
用户和客服通过文字回复沟通
    ↓
客服将工单改为 resolved
    ↓
用户确认结果
    ├── 问题已解决：closed
    └── 问题未解决：重新变为 in_progress
```

### 7.3 工单撤销流程

```text
用户创建工单
    ↓
工单仍为 open 且负责人为空
    ↓
用户点击撤销并二次确认
    ↓
工单变为 closed
    ↓
时间线记录“用户撤销”
```

撤销通过操作类型与正常解决后的关闭进行区分，但两种情况最终状态都为 `closed`。

### 7.4 客服领取流程

```text
客服打开待领取列表
    ↓
选择工单并点击领取
    ↓
后端检查状态为 open 且负责人为空
    ↓
使用数据库条件更新负责人
    ├── 更新成功：写入领取记录并返回成功
    └── 更新失败：返回 409，提示已被其他客服领取
```

### 7.5 管理员分配流程

```text
管理员打开工单详情
    ↓
选择启用状态的客服
    ↓
确认分配或重新分配
    ↓
后端更新负责人并写入操作记录
    ↓
前端刷新工单详情
```

### 7.6 用户角色调整流程

```text
管理员打开用户管理
    ↓
选择普通用户或客服
    ↓
调整角色或账号状态
    ↓
后端检查安全限制
    ↓
更新用户并写入用户管理记录
```

客服存在尚未结束的负责工单时，不能直接降级为普通用户或被禁用。管理员需要先重新分配这些工单。

## 8 总体系统架构

### 8.1 架构图

```text
浏览器
  │
  ▼
Vue 3 前端
  ├── Vue Router：页面路由和角色守卫
  ├── Pinia：登录用户与 Token 状态
  ├── Axios：HTTP 请求和统一拦截
  └── Element Plus：页面组件
  │
  │ HTTP + JSON + JWT
  ▼
FastAPI 后端
  ├── API：接收请求和返回响应
  ├── Schema：参数与响应校验
  ├── Service：权限和业务规则
  ├── Repository：数据库查询与更新
  ├── Model：数据库表映射
  └── Core：配置、认证、安全和异常
  │
  ▼
SQLAlchemy Async + asyncmy
  │
  ▼
MySQL 8
```

### 8.2 架构原则

- 前端和后端分别启动，通过 HTTP 接口通信。
- 前端不直接访问数据库。
- 后端是业务规则和权限判断的最终执行者。
- 页面隐藏按钮不能代替后端权限检查。
- API 层不直接堆积复杂数据库查询和业务规则。
- Service 层负责业务流程、权限、事务和并发控制。
- Repository 层负责可复用的数据访问操作。
- Model 与 Schema 分离，避免直接把数据库对象作为外部请求格式。
- 当前采用单体后端，不拆分微服务。

## 10 前后端职责划分

### 10.1 前端职责

- 提供登录、注册和三个角色的业务页面。
- 保存和恢复前端登录状态。
- 根据角色控制路由和菜单显示。
- 收集表单数据并进行基础校验。
- 调用后端 API 并显示返回结果。
- 统一展示加载、成功、错误和空数据状态。
- 对危险操作提供二次确认。
- 在收到 `401` 时清理登录状态并跳转登录页。
- 在收到 `409` 时提示冲突并刷新相关数据。

### 10.2 后端职责

- 校验所有请求数据。
- 注册用户、验证密码并签发 JWT。
- 验证当前用户身份、角色和账号状态。
- 检查工单的数据归属和操作权限。
- 执行工单状态流转规则。
- 执行领取、分配、回复和用户管理逻辑。
- 使用事务保证数据和操作记录一致。
- 处理客服并发领取冲突。
- 持久化业务数据到 MySQL。
- 返回统一响应和可理解的错误信息。

### 10.3 共同约定

- 时间通过后端统一生成并返回。
- 创建人、操作人和负责人不能由前端任意伪造。
- 枚举值使用英文，页面展示中文名称。
- API 使用 JSON 传输业务数据。
- Token 使用 `Authorization: Bearer <token>` 携带。
- 接口统一使用 `/api/v1` 前缀。

## 13 数据模型概览

系统包含五张核心业务表。

### 13.1 `users`

用途：保存用户账号、角色和启用状态。

主要数据：

- 用户唯一标识
- 用户名
- 邮箱
- 密码哈希
- 角色：`user`、`agent`、`admin`
- 是否启用
- 创建时间
- 更新时间

关键规则：

- 邮箱全局唯一。
- 密码只保存 Argon2 哈希。
- 新注册账号固定为 `user`。
- 管理员不能禁用自己。

### 13.2 `tickets`

用途：保存工单当前主体和当前状态。

主要数据：

- 工单唯一标识
- 对外展示的唯一工单编号
- 标题
- 问题描述
- 分类
- 优先级
- 当前状态
- 创建人
- 当前负责人，可为空
- 分配时间，可为空
- 创建时间
- 更新时间
- 关闭时间，可为空

关键规则：

- 创建人不能为空。
- 负责人必须是启用状态的客服。
- 新工单状态为 `open`，负责人为空。
- 工单不进行物理删除。
- 工单编号生成算法在后端设计文档中确定，但必须唯一且适合搜索和展示。

### 13.3 `ticket_comments`

用途：保存用户与客服的文字回复。

主要数据：

- 回复唯一标识
- 所属工单
- 回复人
- 回复内容
- 回复时间

关键规则：

- 内容不能为空。
- 已关闭工单不能新增回复。
- 普通用户只能回复自己的工单。
- 客服只能回复自己负责的工单。

### 13.4 `ticket_activity_logs`

用途：保存工单关键操作和状态时间线。

主要数据：

- 记录唯一标识
- 所属工单
- 操作类型
- 操作人
- 原状态，可为空
- 新状态，可为空
- 原负责人，可为空
- 新负责人，可为空
- 操作说明，可为空
- 操作时间

主要操作类型：

- `created`
- `updated`
- `cancelled`
- `claimed`
- `assigned`
- `reassigned`
- `status_changed`
- `reopened`
- `closed`

### 13.5 `user_admin_logs`

用途：保存管理员对用户角色和启用状态的修改。

主要数据：

- 记录唯一标识
- 被操作用户
- 操作管理员
- 操作类型
- 原角色和新角色，可为空
- 原启用状态和新启用状态，可为空
- 操作时间

主要操作类型：

- `role_changed`
- `account_enabled`
- `account_disabled`

### 13.6 数据关系

```text
users 1 ─── N tickets               创建人关系
users 1 ─── N tickets               负责人关系
tickets 1 ─── N ticket_comments

users 1 ─── N ticket_activity_logs  操作人关系

```

## 16 账号与安全设计

### 16.1 注册参数

- 用户名长度为 2～30 个字符。
- 邮箱必须符合邮箱格式并且全局唯一。
- 密码长度为 8～64 个字符。
- 密码至少包含一个字母和一个数字。
- 确认密码只用于前端交互和请求校验，不保存到数据库。

### 16.2 密码安全

- 密码使用 Argon2 哈希保存。
- 数据库、日志和响应中不得出现明文密码。
- 登录失败统一提示“邮箱或密码错误”。
- 修改密码成功后，前端清理 Token 并返回登录页。

### 16.3 JWT

- 只使用 Access Token。
- Token 有效期为 2 小时。
- JWT 密钥通过后端环境变量提供。
- Token 中至少包含用户标识、角色和过期时间。
- 后端不能只相信 Token 中的启用状态，每次受保护请求仍需确认用户存在且未禁用。

### 16.4 前端 Token

- Token 暂时保存在 `localStorage`。
- Axios 请求拦截器自动携带 Token。
- `401` 响应触发统一退出流程。
- 前端不保存用户密码。
- 文档需要说明 `localStorage` 方案适用于当前学习项目，正式生产环境可以升级为 HttpOnly Cookie。

### 16.5 跨域

- 后端只允许项目需要的本地前端地址。
- 默认开发地址为 `http://localhost:5173`。
- 不允许在携带认证信息时无条件开放所有来源。

## 17 权限设计

### 17.1 权限判断顺序

后端处理受保护请求时，按照以下顺序检查：

```text
Token 是否存在且有效
    ↓
用户是否存在且启用
    ↓
用户角色是否允许执行该操作
    ↓
目标数据是否存在
    ↓
数据归属是否满足要求
    ↓
当前业务状态是否允许操作
```

### 17.2 权限矩阵


| 操作           | 普通用户       | 客服                           | 管理员                 |
| ---------------- | ---------------- | -------------------------------- | ------------------------ |
| 公开注册       | 允许           | 不允许直接注册为客服           | 不允许直接注册为管理员 |
| 创建工单       | 允许           | 不作为客服工作功能             | 不作为管理功能         |
| 查看个人工单   | 允许           | 允许查看自己作为用户创建的工单 | 允许查看全部           |
| 查看待领取工单 | 不允许         | 允许                           | 允许                   |
| 查看全部工单   | 不允许         | 不允许                         | 允许                   |
| 领取工单       | 不允许         | 允许                           | 不允许                 |
| 分配工单       | 不允许         | 不允许                         | 允许                   |
| 回复工单       | 自己创建的工单 | 自己负责的工单                 | 默认只查看             |
| 开始处理和解决 | 不允许         | 自己负责的工单                 | 不绕过流程             |
| 重新打开和关闭 | 自己创建的工单 | 不允许                         | 不绕过流程             |

## 18 工单状态设计

### 18.1 合法流转


| 原状态        | 新状态        | 操作人         | 说明               |
| --------------- | --------------- | ---------------- | -------------------- |
| `open`        | `in_progress` | 当前负责人客服 | 开始处理           |
| `in_progress` | `resolved`    | 当前负责人客服 | 客服认为已解决     |
| `resolved`    | `in_progress` | 工单创建人     | 用户重新打开       |
| `resolved`    | `closed`      | 工单创建人     | 用户确认解决       |
| `open`        | `closed`      | 工单创建人     | 仅限未分配工单撤销 |

### 18.2 状态限制

- 领取和分配负责人不自动改变状态。
- `open → in_progress` 前必须存在负责人。
- 非当前负责人不能把工单改为处理中或已解决。
- 用户不能直接把 `open` 或 `in_progress` 标记为正常关闭。
- `closed` 是终止状态，不允许回复、修改、重新分配或再次流转。
- 非法流转返回业务错误，不修改数据库。

## 19 事务与并发设计

以下操作必须在单个数据库事务中完成：

- 领取工单并写入领取记录
- 分配或重新分配工单并写入分配记录
- 修改状态并写入状态记录
- 撤销、重新打开或关闭工单并写入记录
- 修改用户角色并写入用户管理记录
- 启用或禁用账号并写入用户管理记录

任意一步失败，整个事务回滚，避免业务数据已经变化但操作记录缺失。

### 19.1 客服并发领取

领取操作不能采用“先查询负责人为空，再普通更新”的非原子方式。后端需要执行带条件的更新：

```text
仅当 assignee_id 仍为空且状态仍为 open 时更新负责人
```

根据数据库实际影响行数判断结果：

- 影响一行：领取成功，写入活动记录并提交事务。
- 影响零行：重新读取工单；若已被领取或状态变化，返回 `409 Conflict`。

### 19.2 角色调整限制

- 客服仍负责任何未关闭工单时，不能降级为普通用户。
- 客服仍负责任何未关闭工单时，不能被禁用。
- 管理员需要先重新分配相关工单。
- 管理员不能禁用自己的账号。

## 20 错误处理设计

### 20.1 后端规则

- 统一捕获认证、权限、数据不存在、业务冲突和校验错误。
- 不向客户端返回堆栈、SQL、数据库连接信息或密钥。
- 未知异常向客户端返回通用提示，并在后端控制台记录必要信息。
- 日志不得记录明文密码、JWT 和数据库密码。

### 20.2 前端规则

- 优先展示后端返回的中文 `message`。
- 表单错误尽量显示在对应字段附近。
- 网络断开或后端不可访问时显示统一网络错误提示。
- `401`：清除认证状态并跳转登录页。
- `403`：提示没有权限。
- `404`：提示目标数据不存在，并允许返回列表。
- `409`：提示数据已变化或工单已被领取，并刷新当前数据。
- `500`：提示系统暂时不可用。

### 20.3 页面状态

所有主要页面都需要处理：

- 初次加载
- 加载成功
- 无数据
- 请求失败
- 提交中
- 提交成功
- 提交失败

## 25 最终演示流程

建议准备三个演示账号：普通用户、客服和管理员。

```text
1. 普通用户注册并登录
2. 创建一张高优先级技术问题工单
3. 查看“我的工单”和详情页
4. 客服登录并查看待领取工单
5. 客服领取该工单
6. 客服把工单改为处理中并回复用户
7. 普通用户补充问题信息
8. 客服回复并标记为已解决
9. 普通用户确认解决并关闭工单
10. 管理员查看工单时间线
11. 管理员演示用户角色和账号状态管理
```

额外演示一个冲突场景：两个客服尝试领取同一工单，第二个客服收到明确的冲突提示。
