# 首次响应 SLA 与 Redis 调度设计

状态：用户于2026-11-03确认实施，代码及本地验证见运行指南。

依据：桌面《Python后端与HelpFlow项目学习路线》中“SLA 与 Redis 服务保障”及“可靠性验收与复盘”。已有通知唯一键、业务事务和工单行锁，继续复用。

## 方案选择

1. 推荐 MySQL 保存规则、快照与结果，Redis ZSET 建立待办索引，独立扫描进程检测，数据库周期补偿。满足路线中的故障恢复要求，增加一个可选 Redis 服务和一个扫描进程。
2. 仅数据库轮询：运行简单，可作为 Redis 不可用时的降级路径，但到期查询负载由数据库承担。
3. 引入任务队列或 Outbox：适合进一步扩展投递系统，但超出当前单机调度范围，暂不采用。

## 规则和时间

第一版按自然时间计算，统一使用 UTC。建议初始时限为 low 24小时、normal 8小时、high 2小时、urgent 1小时，提醒窗口为截止前15分钟。时限必须为正数；规则有版本，修改规则只影响新建工单。提供管理脚本配置规则，不新增规则管理页面。

创建工单时在同一数据库事务内保存规则版本、创建时优先级、时限秒数、起算时间和截止时间。之后修改优先级、分配、转交、重新打开都不重算截止时间。迁移前的既有工单不追溯创建 SLA，界面显示“未启用 SLA”，避免产生虚假的历史逾期和通知。

只有当前负责且授权的客服首次公开回复计为首次响应；内部备注、普通用户补充和管理员操作都不计入。首次响应以取得工单行锁后生成的 UTC 时间记录，并与该回复采用相同时间值。新增 SLA 时间字段使用微秒精度，避免 MySQL 秒级截断改变边界判断。

首次响应时间小于或等于截止时间视为按时，大于截止时间视为逾期。未响应且当前时间严格大于截止时间也是逾期。逾期事实与扫描器是否已通知分开：筛选和显示直接依据数据库时间字段，扫描延迟不能让逾期工单显示为按时。

取消或关闭且尚未发生升级时终止等待；已记录的逾期、升级和晚响应不清除。没有发生首次响应便关闭的工单不会在关闭后补发升级通知。客服晚响应时必须在同一事务中记录逾期升级，防止回复先完成导致扫描器漏记。

## 数据和事务

新增版本化 SLA 规则表、每工单 SLA 快照表，以及提醒/升级事件表。快照包含等待终止时间和首次响应时间；事件唯一约束为工单、SLA版本、事件类型，分别防止重复提醒和重复升级。添加等待状态与截止时间的组合索引，支持数据库补偿和统计查询。

新增 SLA 服务集中处理规则快照、首次响应、终止等待和幂等升级；现有 TicketService 在创建、公开回复、关闭和取消的事务中调用。扫描、公开回复和关闭均先锁定同一工单，再读取或更新 SLA，保持一致的锁顺序。首次响应、超时结果、升级事件及通知必须一起提交或一起回滚。

提醒及升级通知发送给当前启用的负责客服和启用管理员，收件人去重；无负责人时通知管理员。复用 notifications 唯一事件键，消息只包含固定文案和工单引用。通知与升级记录不赋予额外访问权限，转交后的旧客服仍不能读取工单。

## 调度和恢复

Redis ZSET 成员为工单ID与SLA版本，score 为截止时间；Redis 不保存业务事实。独立脚本提供持续运行、单轮扫描及重建入口，扫描间隔建议5秒，数据库补偿周期建议60秒，批量大小建议100，均可配置。

创建工单提交后再尝试加入 Redis；首次响应或关闭提交后再尝试清理 Redis。Redis 连接与命令使用有限超时，失败只记录不含凭据的错误，不改变已经成功的工单操作。扫描器收到成员后重新查询 MySQL、锁定工单、核对版本与当前状态，事务提交成功后才清理已完成成员。

扫描器分批检查截止前15分钟内的成员以产生一次提醒，并检查真正逾期成员以产生一次升级。已提醒但未截止的成员保留至升级或终止；扫描使用完整的分批遍历，避免相同的已提醒成员占满首批导致其他工单饥饿。每条工单独立事务，单条失败不阻塞整批。

数据库补偿使用有界分页遍历有效等待记录及未完成升级的晚响应记录；任务每轮保持公平推进，Redis 数据全丢失时也能逐批恢复。Redis 不可用时仍直接从数据库处理提醒和到期升级。恢复后重建待办索引，幂等判断仍由 MySQL 完成，不依赖 Redis 删除或锁成功。

输出待检查数量、逾期待升级数量、最早逾期待办时间、处理数量、失败数量、实际提醒/升级延迟和补偿数量；记录实测值，不预先承诺精确秒级送达。进程退出不删除数据库待办，重启后通过补偿恢复。

## API 和界面

扩展工单响应中的 SLA 摘要：是否启用、规则版本、截止时间、首次响应时间、按时/等待/即将超时/已超时/已终止状态。详情通过受现有工单权限保护的接口读取提醒和升级记录。

扩展列表查询增加 sla=due_soon|overdue 筛选，始终与现有角色、负责人和状态条件组合；首页增加相应统计与跳转入口。客服首页统计继续限定本人负责工单，待领取列表保持独立。详情展示 SLA 时间和结果，所有时间通过现有前端日期工具按本地时区显示。

过往已超时工单即使后来回复仍保留逾期标记；已终止且从未逾期升级的工单不计入待处理超时提醒。记录展示不包含内部备注、转交原因或其他受限内容。

## 文件职责和交付

- backend/app/models、alembic：SLA 规则、快照、事件及迁移；不启动时自动建表。
- backend/app/services/sla.py：首次响应与升级规则、事务内通知。
- backend/app/services/tickets.py：接入已有创建、回复与关闭事务。
- backend/app/repositories、schemas.py、routers：授权查询、筛选、统计及接口契约。
- backend/app 的 Redis 适配模块及 backend/scripts：ZSET 操作、独立扫描、降级补偿、规则配置及测量。
- frontend/src/views 和 api：首页、列表和详情中的 SLA 展示与筛选。
- backend/tests、frontend 测试：业务、并发、故障恢复和页面回归。
- README、docs/guides、OpenAPI：配置、启动、迁移、演示、故障恢复及真实验证结果。

## 验收

1. 截止前、恰好截止、截止后首次响应；备注、用户回复、管理员操作不算首次响应。
2. 转交、修改优先级及重新打开不重置快照；取消/关闭停止等待，已有逾期保留。
3. 重复扫描、两个扫描器、扫描与首次回复/关闭竞争，均只产生一次同版本同类型事件和对应通知。
4. 通知写入失败、业务提交失败整体回滚；Redis 失败不影响业务成功。
5. 提交后 Redis 写入前退出、Redis 清空、Redis 断连、重启与重建均可通过数据库补偿恢复。
6. 大于单批数量的待办均能处理，失败工单不会饿死后续记录；记录积压和延迟实测。
7. 角色数据范围、转交后旧客服权限、筛选统计一致性及前端跳转回归通过。
8. 在独立测试库和隔离 Redis 命名空间验证；运行既有后端、前端测试、生产构建和相关浏览器流程。未能运行的项目明确记录。

当前 SLA 模块不包含工作日历、多轮 SLA、共享登录限流、统计缓存、任务队列和 RAG。
