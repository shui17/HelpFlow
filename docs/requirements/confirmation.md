## 2 文档目的

本文件用于确认 HelpFlow 项目需要解决的问题、面向的用户、需要具备的功能、主要业务规则和整体验收标准。

本文件只回答“项目要做什么”，不详细规定“代码怎么写”。以下内容留到后续 `docs/requirements/prd.md`、前端设计文档和后端设计文档中确定：

- 页面组件和代码拆分方式
- 每个开发阶段的具体任务
- 前后端框架的初始化命令

后续文档必须遵守本需求确认书。需要改变已经确认的业务规则时，应先修改本文件，再同步修改 PRD 和前后端设计文档。

## 3 项目背景

企业在向客户提供产品或服务时，需要接收并处理账号、支付、产品使用和技术故障等问题。如果只通过即时聊天、电话或普通邮件处理，容易出现以下情况：

- 用户的问题没有统一编号，难以持续追踪。
- 多名客服可能重复处理同一个问题。
- 客服不知道哪些问题尚未处理。
- 管理员难以判断工单由谁负责。
- 问题解决过程和状态变化无法完整保留。
- 用户无法随时查看自己的问题处理进度。

HelpFlow 使用工单作为问题处理载体，让用户、客服和管理员在统一流程中完成问题提交、领取、分配、沟通、解决和关闭。

## 4 项目目标

### 4.1 业务目标

- 为普通用户提供统一的问题提交和进度查询入口。
- 为客服提供清晰的待处理列表和个人工作台。
- 为管理员提供工单分配和用户管理能力。
- 保证每张工单在同一时间只有一名负责人。
- 保存工单回复、状态变化和关键操作记录。
- 通过权限控制阻止越权查看和修改数据。

### 4.2 项目成果目标

- 完成一个可以在本地启动的前后端分离项目。
- 用户可以通过浏览器完成完整业务流程，不依赖 Swagger 操作系统。
- 前端页面能够调用后端接口并正确展示结果。
- 后端数据能够持久化保存到 MySQL。
- 核心接口能够使用 Apifox 独立测试。
- 项目包含明确的环境要求和启动说明。

### 4.3 成功标准

当普通用户、客服和管理员能够分别使用自己的账号，在浏览器中完整完成一次工单从创建到关闭的流程，并且权限、状态和并发领取规则均符合本文档要求时，项目达到基本成功标准。

## 5 用户角色

系统包含三种角色。

### 5.1 普通用户 `user`

普通用户是问题的提交者，可以：

- 自行注册和登录。
- 查看自己的个人信息。
- 创建工单。
- 查看、搜索和筛选自己的工单。
- 查看自己工单的详情、回复和处理记录。
- 在符合条件时修改或撤销自己的工单。
- 在自己的工单中发送文字回复。
- 对未真正解决的工单执行重新打开。
- 确认问题解决后关闭工单。
- 修改自己的密码并退出登录。

### 5.2 客服人员 `agent`

客服人员是工单的处理者，可以：

- 使用管理员授予的客服账号登录。
- 查看无人负责的待处理工单。
- 主动领取待处理工单。
- 查看自己负责的工单。
- 查看工单详情、用户回复和处理记录。
- 在自己负责的工单中发送文字回复。
- 按照规定修改工单状态。
- 查看与本人工作相关的简单工单数量统计。

### 5.3 管理员 `admin`

管理员负责系统管理，可以：

- 查看系统中的全部工单。
- 搜索、筛选和查看任意工单详情。
- 将工单分配或重新分配给客服。
- 查看工单回复和完整处理记录。
- 查看、搜索和筛选用户。
- 将普通用户调整为客服。
- 将客服调整为普通用户。
- 启用或禁用账号。
- 查看系统范围内的简单工单数量统计。

管理员默认不作为客服参与工单对话。如果管理员需要实际处理工单，应使用客服角色账号。

## 6 账号与身份认证需求

### 6.1 账号产生规则

- 普通用户可以通过公开注册页面自行注册。
- 公开注册只能产生普通用户账号。
- 公开注册不能创建客服或管理员账号。
- 客服账号由管理员将普通用户调整为客服后产生。
- 系统的第一个管理员通过初始化方式创建。
- 普通用户不能通过页面或公开接口将自己升级为客服或管理员。
- 管理员不能通过普通用户管理页面直接产生新的管理员。

### 6.2 登录规则

- 用户使用邮箱和密码登录。
- 登录成功后，后端返回 JWT Access Token。
- 前端将 Token 暂时保存在 `localStorage`。
- 前端通过 Axios 在请求头中自动携带 Token。
- Token 过期后，用户返回登录页面并重新登录。
- 系统暂不提供 Refresh Token 和“记住我”功能。
- 已被禁用的账号不能登录。
- 用户修改密码后，应重新登录。

### 6.3 密码规则

- 数据库不得保存明文密码。
- 密码必须经过安全哈希后保存。
- 登录时使用哈希校验密码。
- 前端需要提供新密码与确认密码一致性校验。
- 后端必须再次校验密码是否符合规则，不能只依赖前端校验。

具体密码长度和复杂度在 PRD 中确定。

## 7 工单需求

### 7.1 工单基本信息

用户创建工单时需要填写：

- 工单标题
- 问题描述
- 问题分类
- 优先级

系统自动产生或记录：

- 工单编号
- 创建人
- 当前状态
- 当前负责人
- 创建时间
- 更新时间

### 7.2 问题分类

系统提供以下固定分类：

- 账号问题
- 产品问题
- 支付问题
- 技术问题
- 其他

### 7.3 优先级

系统提供以下优先级：

- 低
- 普通
- 高
- 紧急

### 7.4 创建默认值

- 新工单状态默认为“待处理”。
- 新工单负责人默认为空。
- 创建人根据当前登录用户自动确定，不能由前端任意指定。

### 7.5 修改规则

- 用户只能修改自己创建的工单。
- 只有状态为“待处理”并且尚未分配客服的工单可以修改主体内容。
- 可修改内容包括标题、问题描述、问题分类和优先级。
- 客服领取或管理员分配后，用户不能修改工单主体，只能通过回复补充信息。
- 客服和管理员不能直接修改用户最初提交的问题内容。

### 7.6 撤销和删除规则

- 系统不提供永久删除工单功能。
- 用户误提交工单时，可以在工单仍为“待处理”且无人负责时撤销。
- 撤销后的工单按照“已关闭”处理并保留记录。
- 已经被领取或分配的工单不能直接撤销，应按照正常处理流程解决和关闭。

## 8 工单分配需求

系统同时支持客服主动领取和管理员指定分配。

### 8.1 客服主动领取

- 客服可以查看状态为“待处理”且没有负责人的工单。
- 客服可以主动领取其中一张工单。
- 领取成功后，该客服成为工单唯一负责人。
- 领取操作本身不自动把状态改为“处理中”。
- 客服开始处理时，再主动把状态改为“处理中”。

### 8.2 管理员指定分配

- 管理员可以把未分配工单指定给某位客服。
- 管理员可以根据实际情况重新分配已经有负责人的工单。
- 被分配的目标账号必须是处于启用状态的客服账号。
- 每次分配和重新分配都需要记录操作人和操作时间。

### 8.3 并发领取规则

- 一张工单同一时间只能有一名负责人。
- 两名客服同时领取同一张工单时，只允许一人成功。
- 未领取成功的一方必须收到明确的冲突提示。
- 系统不能出现同一工单同时属于两名客服的情况。

## 9 工单状态需求

### 9.1 状态定义

| 状态值 | 中文名称 | 含义 |
| --- | --- | --- |
| `open` | 待处理 | 工单已经创建，等待客服领取或开始处理 |
| `in_progress` | 处理中 | 客服正在处理工单 |
| `resolved` | 已解决 | 客服认为问题已经解决，等待用户确认 |
| `closed` | 已关闭 | 工单流程结束，只允许查看 |

### 9.2 正常状态流程

```text
待处理 open
    ↓
处理中 in_progress
    ↓
已解决 resolved
    ↓
已关闭 closed
```

### 9.3 重新打开

用户认为问题没有真正解决时，可以执行：

```text
已解决 resolved
    ↓
处理中 in_progress
```

重新打开后，原负责人继续负责该工单。

### 9.4 状态操作权限

- 负责该工单的客服可以将“待处理”改为“处理中”。
- 负责该工单的客服可以将“处理中”改为“已解决”。
- 工单创建人可以将“已解决”改为“已关闭”。
- 工单创建人可以将“已解决”重新改为“处理中”。
- 管理员可以查看和管理工单，但不得绕过正常业务流程任意修改状态。
- 已关闭工单不能再次修改状态。
- 所有不符合流程的状态修改必须被后端拒绝。

## 10 工单回复需求

- 回复形式为纯文字。
- 每条回复需要保存回复人、回复内容和回复时间。
- 普通用户只能回复自己创建的工单。
- 客服只能回复自己负责的工单。
- 管理员可以查看全部回复，但默认不参与对话。
- 已关闭工单不能继续回复。
- 回复不要求实时推送，用户刷新页面后可以看到新回复。
- 系统不提供图片、文件、语音和视频附件。

## 11 工单处理记录需求

每张工单需要保存并展示独立的处理时间线，至少记录：

- 工单创建
- 用户撤销
- 客服领取
- 管理员分配
- 管理员重新分配
- 工单状态变化
- 用户重新打开工单
- 用户关闭工单

每条记录需要包含：

- 操作类型
- 操作人
- 操作对象
- 操作时间
- 状态变化前后的值或必要说明

用户和客服的文字回复保存在独立的沟通记录中，不与操作时间线混为一组数据。

## 12 查询、筛选和排序需求

工单列表需要支持：

- 分页查看
- 按工单状态筛选
- 按优先级筛选
- 按问题分类筛选
- 按负责人筛选，适用于客服和管理员页面
- 使用工单标题或工单编号搜索
- 按创建时间升序或降序排列
- 清空全部筛选条件

普通用户的查询结果只能包含自己创建的工单。客服只能查看待领取工单和自己负责的工单。管理员可以查看全部工单。

系统暂不提供复杂全文检索和高级组合查询。

## 13 用户管理需求

管理员可以：

- 查看用户列表。
- 使用用户名或邮箱搜索用户。
- 按角色筛选用户。
- 按启用或禁用状态筛选用户。
- 查看用户基本信息、角色、账号状态和注册时间。
- 将普通用户调整为客服。
- 将客服调整为普通用户。
- 启用或禁用账号。

限制规则：

- 系统不提供永久删除用户功能。
- 管理员不能禁用自己的账号。
- 普通用户不能通过用户管理功能被直接设置为管理员。
- 被禁用的账号不能登录。
- 对角色和账号状态的修改需要记录操作人和操作时间。

## 14 权限需求

### 14.1 基本原则

- 所有业务接口必须由后端进行身份和权限校验。
- 前端隐藏菜单或按钮不能代替后端权限校验。
- 用户只能访问自己有权查看的数据。
- 未登录用户不能访问需要登录的页面和接口。
- 用户登录状态失效后，前端应引导用户重新登录。

### 14.2 权限矩阵

| 操作 | 普通用户 | 客服 | 管理员 |
| --- | --- | --- | --- |
| 自行注册 | 允许 | 不允许直接注册为客服 | 不允许直接注册为管理员 |
| 创建工单 | 允许 | 不作为客服工作功能 | 不作为管理功能 |
| 查看自己的工单 | 允许 | 允许查看自己作为用户创建的工单 | 允许 |
| 查看待领取工单 | 不允许 | 允许 | 允许 |
| 查看全部工单 | 不允许 | 不允许 | 允许 |
| 领取工单 | 不允许 | 允许 | 不允许 |
| 分配或重新分配工单 | 不允许 | 不允许 | 允许 |
| 回复工单 | 仅自己的工单 | 仅自己负责的工单 | 默认只查看 |
| 修改工单状态 | 关闭或重新打开自己的工单 | 修改自己负责工单的处理状态 | 不绕过正常流程 |
| 管理用户角色 | 不允许 | 不允许 | 允许 |
| 启用或禁用用户 | 不允许 | 不允许 | 允许 |

## 15 前端页面需求

### 15.1 公共页面

- 登录页
- 普通用户注册页

### 15.2 普通用户页面

- 用户首页概览
- 我的工单列表
- 创建工单页面
- 工单详情页面
- 个人中心
- 修改密码页面

### 15.3 客服页面

- 客服工作台
- 待领取工单列表
- 我负责的工单列表
- 工单详情与回复页面
- 个人中心
- 修改密码页面

### 15.4 管理员页面

- 管理数据概览
- 全部工单列表
- 工单详情与分配页面
- 用户管理页面
- 个人中心
- 修改密码页面

### 15.5 页面交互要求

- 使用左侧菜单和顶部导航组成后台管理布局。
- 根据用户角色显示不同菜单。
- 表格需要具有分页、筛选、搜索和空数据状态。
- 表单需要显示必填项和明确的校验错误。
- 所有接口请求需要显示加载状态。
- 操作成功后需要显示成功提示。
- 操作失败后需要显示用户可理解的错误提示。
- 撤销、关闭、禁用、重新分配等重要操作需要二次确认。
- 工单状态和优先级需要使用容易区分的标签展示。
- 页面以电脑端为主，保证常见笔记本分辨率下正常使用。
- 不要求单独开发手机端。
- 不制作与业务无关的复杂动画和视觉效果。

## 16 简单数据概览需求

### 16.1 普通用户概览

展示当前用户不同状态的工单数量，例如：

- 待处理
- 处理中
- 已解决
- 已关闭

### 16.2 客服工作台概览

展示与当前客服相关的数据，例如：

- 当前待领取工单数量
- 本人处理中的工单数量
- 本人已解决工单数量

### 16.3 管理员概览

展示系统范围内的简单统计，例如：

- 各状态工单数量
- 当前启用的普通用户数量
- 当前启用的客服数量

当前只要求使用数字卡片或简单列表，不要求复杂统计图表和数据分析。

## 17 技术边界

本阶段已经确认以下基础技术范围，详细配置在 PRD 中确定。

| 部分 | 技术选择 |
| --- | --- |
| 系统架构 | 前后端分离 |
| 前端 | Vue 3、Vite、Axios、Element Plus |
| 后端 | Python、FastAPI、SQLAlchemy、Alembic |
| 数据库 | MySQL |
| 身份认证 | JWT Access Token |
| 接口测试 | Apifox |
| 运行方式 | 本地运行和浏览器演示 |

当前项目不把 pytest、GitHub、GitHub Actions 和 Swagger 作为必须交付内容。FastAPI 即使具备自动生成 OpenAPI 文档的能力，也不依赖 Swagger 完成项目演示。

## 18 接口测试需求

使用 Apifox 建立开发环境、测试账号和接口用例，至少覆盖：

- 普通用户注册、登录和获取个人信息
- 创建、修改、查询和撤销工单
- 不同普通用户之间的越权访问拦截
- 客服查看并领取待处理工单
- 两名客服领取同一工单时的冲突处理
- 管理员分配和重新分配工单
- 用户与客服回复工单
- 合法状态流转
- 非法状态流转拦截
- 已关闭工单禁止修改和回复
- 管理员调整用户角色
- 管理员启用和禁用账号
- 参数错误
- 未登录访问
- 无权限访问
- 资源不存在
- 业务冲突

接口测试通过后，前端再正式接入相应接口进行联调。

## 19 本地运行和展示需求

- 后端能够在本地启动 FastAPI 服务。
- 前端能够通过 Vite 在本地启动。
- 数据持久化到本机 MySQL 8。
- 前端能够正确访问后端接口。
- 前后端跨域配置只允许项目需要的本地地址。
- 项目需要提供清晰的环境变量示例，但不得包含真实密码和密钥。
- 项目需要提供数据库初始化说明。
- 项目需要提供前端和后端启动说明。
- 项目主要通过浏览器演示，不把 Swagger 作为主要演示页面。

建议演示流程：

1. 注册一个普通用户并登录。
2. 创建一张工单。
3. 使用客服账号登录并领取工单。
4. 客服把工单改为“处理中”并回复用户。
5. 用户登录并补充信息。
6. 客服把工单标记为“已解决”。
7. 用户确认后关闭工单。
8. 管理员登录并查看工单处理记录和用户信息。

## 21 整体验收标准

### 21.1 账号与权限

- [ ] 普通用户可以注册和登录。
- [ ] 客服和管理员不能通过公开注册直接产生。
- [ ] 管理员可以调整普通用户与客服角色。
- [ ] 管理员可以启用和禁用账号。
- [ ] 不同角色只能看到和执行自己有权限的内容。
- [ ] 普通用户不能查看其他用户的工单。
- [ ] 客服不能修改不属于自己的工单。

### 21.2 工单流程

- [ ] 普通用户可以创建工单。
- [ ] 工单包含标题、描述、分类和优先级。
- [ ] 用户可以在规定条件下修改或撤销工单。
- [ ] 客服可以领取无人负责的工单。
- [ ] 两名客服不能同时成功领取同一工单。
- [ ] 管理员可以分配和重新分配工单。
- [ ] 用户和负责客服可以发送文字回复。
- [ ] 工单只能按照规定的状态流程变化。
- [ ] 用户可以重新打开未真正解决的工单。
- [ ] 用户可以关闭已经解决的工单。
- [ ] 已关闭工单不能继续修改或回复。
- [ ] 工单操作时间线完整保存并正确展示。

### 21.3 查询与页面

- [ ] 工单列表支持分页。
- [ ] 工单列表支持状态、优先级和分类筛选。
- [ ] 工单列表支持标题或编号搜索。
- [ ] 工单列表支持创建时间排序。
- [ ] 登录、注册、工单、客服和管理页面可以正常使用。
- [ ] 不同角色登录后看到对应的菜单和页面。
- [ ] 页面能够正确显示加载、成功、失败和空数据状态。
- [ ] 危险操作具有二次确认。

### 21.4 数据与接口

- [ ] 数据能够持久化保存到 MySQL。
- [ ] 前后端能够正常调用接口。
- [ ] 后端能够正确处理未登录、无权限、数据不存在和业务冲突。
- [ ] Apifox 中保存主要接口和测试场景。
- [ ] 已确认的核心接口测试全部通过。

### 21.5 运行与交付

- [ ] 前端能够在本地独立启动。
- [ ] 后端能够在本地独立启动。
- [ ] MySQL 初始化步骤明确并可执行。
- [ ] 项目不依赖开发者电脑中未说明的特殊配置。
- [ ] 项目提供完整的本地启动和演示说明。
- [ ] 可以在浏览器中完成一条从工单创建到关闭的完整演示流程。
